# Findings

- [卡顿定位] 人立方（6 声部 844 音符）粘贴整首乱序歌词：粘贴到标注完成 347 ms，长任务 55 / 96 ms（匹配本身 Node 中 30–60 ms）。点“修正 674 个音符”：点击处理同步 15 486 ms，长任务 15 586 ms + 547 ms（排版）。CPU 采样：Vue 深度遍历 un/get/ownKeys ≈ 8.8 s，Re（scheduleRender 内 JSON.stringify 工程）≈ 5.4 s。
- [原因] App.vue `watch(current, …, {deep:true, flush:'sync'})`：applyAlignedLyrics 每写一个音符就同步触发一次，回调后重新深度遍历整个工程并序列化签名、排队保存 -> 674 次 × 全工程。改为默认 pre 刷新后一个 tick 只执行一次。editor.browser 的“同步禁用导出”只要求下一次 Playwright 查询前按钮已禁用，pre 刷新（微任务）满足。
- [WASM] 匹配是整数打分的局部比对，JS 版本在 Worker 中 100 ms 内完成，主要开销不在算法；WASM 需要额外工具链与拼音词典移植，收益小，未采用。
- [复测] 同一场景：点“修正 674 个音符”点击处理 3 ms（原 15 486 ms），到排版完成 678 ms（原 16 188 ms），剩余长任务 517 ms 为 OSMD 重新排版（需要 DOM，只能在页面上）；粘贴整首不再有匹配长任务（剩 54 ms 为输入框标注渲染）。LyricEditor 分块 306.85 kB → 13.24 kB，拼音词典随 Worker 分块（297.69 kB）。
- [启动页] FontFaceSet 自带 status='loaded'，prepare() 把任务返回值的 status 当作步骤状态 -> 字体步骤显示 loaded 而无勾 -> 字体任务返回 null。重载后约 0.1 s 准备就绪，启动画面约 1 s 淡出后恢复工程并排版（请不要带我走 573 音符约 1 s 内完成）。
- [音符合并标准] 没有关于“合并激进程度”的标准；记谱标准只规定结果：同一音高的延续是一个长音或连音线，一个音节唱多个音高是花腔（melisma），连线（slur）覆盖这些音并在音节后画延长线（LilyPond 文档；MusicXML 4.0 extend 示例同时写 slur 与 extend；也有制谱者只用其一）。设置在“谱面设置 → 声部整理 → 合并连续音符”：不合并 / 低（同音延长，符合标准且无损）/ 中（合成器重唱韵母视为同一音节，符合花腔记法）/ 高（再吸收十六分以内的装饰音，超出标准的简化，会删去这些音）。现状只写延长线、不写花腔连线 -> 建议后续补 slur。
